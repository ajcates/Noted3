noted — design notes

Theory · principles · elements · interaction · motion

This is the reasoning behind the nine screens of the noted Android design: a personal markdown vault that lives on the user's own device, served by their own machine, edited on a phone. The document records why the design looks the way it does, catalogues every element it uses, states how those elements are meant to relate to one another, and specifies how they move. It is written so that a second designer or an engineer can extend the app without guessing.

1 · Theory of the design

1.1 The product is a file system with opinions

Every note is a real .md file on disk. The design never hides that. Filenames appear in monospace, paths appear as paths, the index is described in the terms the server actually uses (entries, inverted graph, mtime), and sync is shown as a queue that drains rather than a magic cloud. The theory: a tool for people who chose plain text should keep showing them the plain text. Trust in this app comes from legibility of mechanism, not from concealment of it.

1.2 Two voices: the field guide and Material 3 Expressive

The visual language pairs an editorial, field-guide voice — a serif with real personality for anything the user wrote, monospace for anything the machine owns — with Material 3 Expressive's structural vocabulary: tonal surfaces, generous corner families, a single loud action per screen, a docked bottom bar that carries navigation and the primary verb. The serif supplies authorship; Material supplies affordance. Where they conflict, authorship wins on content and Material wins on chrome.

1.3 Expressiveness is carried by shape, not by decoration

The app has no gradients, no illustration, no drop-shadow stacking, and exactly three accent hues. Its personality comes from the shape system: asymmetric corner families that mirror across a row, cookie-shaped badges for agentic and identity moments, pill ends on the primary action, and a lifted 30px shoulder on the docked bar. Because expressiveness lives in geometry, it survives theming, it costs nothing at render, and it never competes with the user's prose.

1.4 Thumb-first, one-hand-first

Every destructive or committing action is reachable in the bottom third of the screen. The top of the screen is for orientation only — masthead, search field, breadcrumb — and is allowed to scroll away. Menus and panels rise from the bottom edge and are anchored to the control that opened them, so the finger never has to leave the region it was already in.

1.5 Nothing irreversible

The editor has undo. The AI writes proposals, not edits. Every apply is preceded by a snapshot, and every snapshot is browsable and restorable. This is what makes an AI-editing surface acceptable in a personal archive: the cost of a wrong suggestion is one tap, and the user can see that cost before they accept it.

2 · Guiding principles

  1. One loud thing per screen. Ember is the commit colour and appears once: New, Snapshot, Apply, Restore. If a screen has two ember elements, one of them is wrong.
  2. Colour means role, never mood. Ink = link, selection, AI. Moss = health, sync, additions. Ember = commit, unsynced, section rails. A hue never appears outside its role.
  3. Type declares ownership. Serif for what the user wrote, sans for what the app says, mono for what the file system knows. A label in the wrong family is a lie about who wrote it.
  4. Show the mechanism, quietly. Counts, timings, byte sizes and queue depths belong in the interface — small, monospaced, never in the way.
  5. Density is a mode, not a compromise. Snippet cards, folders and tags are three legitimate readings of the same vault; each has its own row height and none is a degraded version of another.
  6. Propose, then commit. Any automated change is rendered as a diff with a count before it can be accepted.
  7. Motion explains hierarchy. Things that come from a control grow out of that control. Things that own the screen rise from the edge. Nothing fades in from nowhere.

3 · Foundations

3.1 Colour

All colour is authored in OKLCH so that lightness can be held constant while hue and chroma move — every accent in the ramp lands at a predictable contrast against the same surface. Three seed hues, four surface steps, one text ramp.

Ink containeroklch(32% 0.11 275)Selected chips, AI avatar, user chat bubble, active nav
Mossoklch(78% 0.07 175)Saved/verified state, backlinks, diff additions, timings

Rules: text carries full-opacity ink, never a translucent tint; a hue on a hue is forbidden (ember text never sits on ink container); the well surface exists only to hold code, diffs and inputs — it is the "recessed" register and reads as machine space.

3.2 Type

Three families, each with a fixed jurisdiction:

  • Fraunces — note titles, screen titles, headings inside prose, the wordmark (italic at 40px), the Aa format glyph. Weight 400–600, optical size high. Never used for a control label.
  • Manrope — all chrome: buttons, chips, row titles, body copy in the editor, panel prose. 700–800 for controls, 400–600 for reading.
  • IBM Plex Mono — filenames, paths, timestamps, counts, diff bodies, section-rail labels, badges (SNAPSHOT), token masks. Uppercase with 0.10–0.14em tracking when used as a rail label.

Scale in use: 40 (wordmark) · 27/24/21 (titles) · 18 (card title) · 16 (editor body) · 15/14.5 (row title, control) · 13 (chip, secondary) · 11–12 (metadata) · 10–11 (rail/badge). Nothing tappable is labelled below 11px, and no body text is below 14px.

3.3 The shape family

Shape is the app's signature and is systematic, not arbitrary:

  • Mirrored squircle, 16/26px — icon buttons. Adjacent buttons alternate the mirror (16/26 then 26/16) so a row of them reads as a rhythm instead of a strip.
  • Card family, 28px with one 12px notch — snippet cards. The notch rotates position card to card, which gives a scrolling list visible variety at zero cost in structure.
  • Menu cells, 26/14 mirrored, 74px tall — the format grid. Each cell is a different member of one family; Bold is filled with ember container to mark active state.
  • Pill (999px) — anything that filters or scopes: chips, the search field, the wikilink/tag/code row.
  • Asymmetric pill, 22px/999px — committing buttons (New, Snapshot, Apply, Restore). The flat end points back at the content it acts on.
  • Cookie (12-point clip) — reserved for two things only: the format badge and the AI avatar. It marks "something acts on your text".
  • Sheet shoulders — 30px on the docked bar, 32px on menus, 36px on AI panels. Elevation reads through corner size, so the stack is legible without shadows.

3.4 Space, density and touch

Screen gutter 18–20px. Card padding 17/18px. Gaps come from flex and grid gap, never margins on siblings — 8px inside a control cluster, 10–12px between cards, 20–22px before a section rail. Row heights: snippet card ~120px, folder row 58px, tag row 52px, file row under a folder 46px with a 30px indent. Every tap target is at least 44×44px, controls in the docked bar are 46px, and menu cells are 74px because they are hit at speed.

3.5 Iconography

Icons are typographic where the concept is typographic (B, I, S, H2, ”, ‹›, [[, #) and glyphic where it is spatial (⌕ search, ⇅ sort, ◎ view mode, ⏱ snapshot, ↶↷ undo/redo, ✦ AI, ▾▴ expander, › drill-in). No icon appears without a label in the format menu; in toolbars, icon-only is allowed because the set is small and permanent. The folder mark is a shape, not an icon — a tab-topped rectangle that fills with ember container when open.

4 · Element catalogue

4.1 Masthead

An ember mono kicker (vault · 214 notes) above a 40px Fraunces italic wordmark, with a single settings squircle at the right. It states scale before identity, which is the honest order for an archive. On non-root screens the masthead collapses to a back squircle plus a two-line identity block (filename in mono, state in sans) — the same slot, less weight.

4.2 Search field and sort button

A full-pill field on the 32% surface, with a detached 46px sort button to its right. The sort button is deliberately outside the field: sorting is a property of the result set, not of the query. It is a two-line control — glyph over a mono key label (SORT when idle, the active key such as REL, MOD, A–Z once chosen) so the current sort is readable without opening anything. It fills with ink container when a non-default sort is active.

The menu it opens is a bottom-anchored sheet of radio rows — Recently edited, Recently created, Title A–Z, Most backlinks, File size — with a direction toggle and a "Group by day" switch. On the search screen the first option is Relevance and the match count stays visible above the results while the sheet is open, because changing sort must be evaluated against the result set.

4.3 Section rail and view-mode switcher

A section rail is an ember mono uppercase label, optionally with a hairline and a count. It is the app's structural punctuation: it tells you what the following rows are grouped by. On the list screen the rail shares its line with the view-mode switcher — a bordered pill with an ◎ glyph, the current mode in mono uppercase, and a caret. Placing the switcher on the rail rather than in the toolbar makes the grammar explicit: the rail describes the grouping, the switcher changes it.

Three modes, each with its own rail text: list (rail: "Recently edited"), folders (rail: the vault path, plus a breadcrumb line), tags (rail: "42 tags · a–z", plus an alphabet index). The switcher fills with ink container when the mode is not the default, so a user who left the app in tag view can see why the screen looks different.

4.4 Snippet card

The list mode's unit: Fraunces title (18px, two lines maximum), a three-line excerpt with wikilinks rendered in ink, then a footer of tag chip, relationship chip ("3 backlinks", "edit queued") and a mono timestamp. An unsynced note grows a 7px ember dot after its title. The card never shows a menu button; long-press is the route to per-note actions, keeping the resting state quiet.

4.5 Folder row and file row

A folder row carries the tab-topped folder mark, a sans name, a mono subtitle stating what is inside ("96 · 2026-09-05 · newest", "unsorted · 3 untitled"), a count and a drill-in chevron. Open folders take ember container and their children appear as file rows indented 30px with a 3px status bar in place of the folder mark. The bar's hue is the note's state: ember unsynced, ink linked, moss synced-and-quiet, grey unresolved. Folder view is the only place a breadcrumb appears.

4.6 Tag row and expander

Every tag in the vault, alphabetical, one per row: a # mark, the tag, a count, and a 34px squircle expander. Tapping the expander — not the row — opens the tag in place: the row takes the card surface, its mark turns ember, the caret flips, and up to three file rows appear beneath, closed by a "20 more in #design" line with an "open tag" pill that navigates to the full filtered list. Tapping the row itself goes straight to that filtered list. Two gestures, two intents, no ambiguity. An A–Z index above the list jumps to first letters and highlights the letter currently at the top of the viewport.

4.7 Docked bar and primary action

A 27%-surface bar with 30px shoulders, pinned to the bottom edge. Left: a cluster of 46px squircles — menu, tags, and the ✦ AI button, the last in ink container because AI is a mode, not a commitment. Right: the ember asymmetric pill, which is the only committing action on the screen ("New" on the list, "Snapshot" in the editor, "Snapshot now" in history). On the search screen the search squircle takes ink container to show where you are. The bar never hides on scroll; it is the app's floor.

4.8 Editor surface

Markdown is rendered live in its final styling — no raw syntax, no split preview. Headings are Fraunces, body is 16px Manrope at 1.6, wikilinks are ink with a 2px underline offset 2px, bullets take an ember marker, code blocks sit on the well surface with a moss left rule. Only the token being typed reveals its syntax: an in-progress [[oklch shows its brackets in mono ink beside a 2px ink caret, and collapses to styled text on completion. Title and tag chips sit above the body, with a dashed "+ tag" affordance. Below the body: a "Backlinks · 2" rail and quoted context lines, so the note's inbound edges are part of the note.

4.9 Wikilink autocomplete

A well-surface list with a 28px radius that appears directly under the caret line: matched titles, the first in ink container, and a final ink-text row "+ Create 'oklch'". It never covers the line being typed, and it is dismissed by any character that closes the token. Existing notes always outrank creation.

4.10 Format pop menu

Opened by the Aa squircle in the editor toolbar; the modifiers are not permanently docked, because they are only meaningful with a selection or an intent. A 32px container floats 14px above the bar and holds: a header with the ember cookie Aa badge, the word "Format" in Fraunces, a mono "selection" qualifier, and a close squircle; a 3×3 grid of 74px shape cells (Bold, Italic, Strike, Heading, List, Quote) whose corner families mirror across the grid, active items filled ember container; and a row of three full pills for Wikilink (ink container), Tag and Code. Grid items are character formats; the pill row inserts structure. Active states are read from the selection and update live as the caret moves.

4.11 Undo, redo and Snapshot

Undo and redo are neighbouring squircles; a disabled step drops to the 52% text tone rather than disappearing, so the pair keeps its shape. The old "Done" is replaced by an ember ⏱ Snapshot pill: leaving the editor is not an event worth a button, but marking a version is. Snapshot is idempotent-feeling — pressing it with no changes since the last version reports "no changes to snapshot" rather than writing a duplicate.

4.12 Version history

Scope chips (Snapshots / Autosaves / All) sit above a selected-version card — a 32px card with a 14px notch, an ember mono "selected · today 09:41" line, a moss +42 −7 count, a four-line diff on the well surface, and the ember "Restore this version" pill beside a compare squircle. Beneath it, a timeline: 12px ink dots for snapshots (the current draft's dot is ember with a halo), 9px grey dots for autosaves, connected by a 2px rule, grouped by day rails. Snapshots get a mono SNAPSHOT badge and a device name; autosaves get a smaller, quieter row. The footer states retention ("keeps 30 days · 214 kB") because a version store that silently grows is a liability.

4.13 AI panel — single note

A bottom sheet with 36px shoulders over a dimmed editor. Header: cookie ✦ avatar, "Edit with AI", and a mono scope line ("this note + 2 backlinks") — the scope is stated before the conversation, because an editing agent's scope is the whole safety story. Body: ink-container user bubbles (26px, 8px tail) on the right, surface assistant bubbles on the left, and beneath the assistant's prose a proposed-diff block on the well surface with a header count. Actions are "Apply both" (ember) and "Review one by one" (outline), followed by a moss ⏱ line: "a snapshot is taken before applying". A row of quick-action chips (Summarize, Suggest links, Fix tags) sits above the composer, and the composer is a well-surface pill with a 52px ink send squircle.

4.14 AI panel — many notes

Same sheet, different unit of work. Scope becomes editable: removable ink chips (#design ×) plus a dashed "+ scope". The assistant's answer is a plan, not prose — a well-surface list of one row per note with an ember checkbox, the filename in mono, and a per-file diff count; excluded rows show an unchecked box and a red "conflict" tag with the note's reason. The commit button counts what it will touch ("Apply to 11"), and the moss line promises one snapshot per note with a batch undo. Bulk editing is only tolerable when the blast radius is enumerated, per file, before the tap.

4.15 Search results

Scope chips (Everything / Titles / Tags / Links), a result meta line pairing "7 notes · 12 matches" with a moss "index · 4ms", then result cards: Fraunces title with matched spans in ink-container highlight, a mono provenance line (filename · tags · backlink count), and a quoted excerpt with the same highlight. A dashed card offers to create the missing note when the query has no title match, and a mono footer notes cached results. Search always tells you how it knew.

4.16 Settings

Ember mono rails (Vault, Auth token, Sync, Appearance) over grouped 28px cards. Values that are really strings from a config file are mono; explanations are sans. The token is masked with wide tracking and a reveal glyph, and its truth is a moss verification line with a timestamp — "Verified against this server 4m ago" — not a green tick. Toggles are 52×32px with ink container when on. The screen ends with a mono status footer (version, index rebuild time).

5 · How the elements must interact

  • One surface at a time. The format menu, the wikilink autocomplete, the sort sheet and the AI panel are mutually exclusive. Opening any one dismisses the others; the AI panel additionally dismisses the keyboard, since it owns the composer.
  • Sort and view mode are independent but not orthogonal. Sort applies within groups: in folder view it orders files inside each folder; in tag view it orders notes inside an expanded tag; in list view it orders the whole list and may replace the day rails. Changing view mode preserves the sort key when the key still makes sense and falls back to A–Z when it doesn't (tags have no mtime).
  • The rail always describes what the rows are. Any change to grouping, sorting or scope must update the rail text and its count in the same frame as the rows. A rail that disagrees with its rows is the worst bug this design can have.
  • Scope flows down, never up. The list's AI panel inherits the active view mode, tag filter and search query as its initial scope chips; the editor's AI panel inherits the open note plus its backlinks. Editing scope inside a panel never changes the list behind it.
  • Every apply writes a version. AI applies, restores and bulk edits all go through the same snapshot path as the Snapshot button, so history is the single audit log. Restoring a version is itself snapshotted, which is why history can never trap the user in the past.
  • Undo and history are one stack, two resolutions. Undo steps through keystroke-level edits in the current session; history steps through committed versions. An AI apply is a single undo step and a single version, so both stacks agree.
  • Format menu obeys the selection. Active cells reflect the current selection's marks; with an empty selection the menu applies to the word under the caret, and block items (Heading, List, Quote, Code) apply to the whole block regardless of selection.
  • Autocomplete outranks the toolbar. While the wikilink list is open the format menu button is inert, and the [[ pill in the menu is disabled — you cannot open a link inside a link.
  • Sync state propagates to every representation of a note. An unsynced note shows the ember dot on its snippet card, an ember status bar in folder and tag views, an ember "queued" timestamp in dense rows, and a pending-writes count in Settings. One fact, one hue, everywhere it is visible.
  • Counts must be live and honest. Vault count, tag counts, folder counts, match counts, pending writes and version counts all come from the index, and all show a stale marker rather than an old number when the index is rebuilding.
  • Tag rows: expander expands, row navigates. This split must hold everywhere the pattern is reused, including inside the AI scope picker.
  • Ember exclusivity. When a sheet with an ember commit button is open, the docked bar's ember button drops to its outline treatment. Only one commit is offered at a time.

6 · Motion

6.1 Motion tokens

Token Curve / duration Used for
spatial-fastspring, ~280ms, damping 0.82Chips, expanders, toggle knobs, press response
spatial-defaultspring, ~420ms, damping 0.8Menus, sheets, list regrouping, shape morphs
spatial-slowspring, ~560ms, damping 0.85Full-screen transitions, view-mode changes
effectscubic-bezier(0.2,0,0,1), 150–200msColour, opacity, highlight, scrim
exitcubic-bezier(0.3,0,0.8,0.15), 200msDismissals — always faster than the entrance

Springs, not eases, for anything that moves or changes size — the shape family only reads as a family when its members morph elastically. Colour never springs; it uses the effects curve so hue changes feel like state, not motion.

6.2 Specified behaviours

  • Press. Every tappable element scales to 0.96 and shifts one surface step brighter over 100ms, releasing on spatial-fast. Icon squircles additionally morph their corner family toward its mirror while held — the press is a shape change. No ripples; the shape system replaces them.
  • Format menu open. The Aa button morphs into the menu: the menu scales from 0.9 with its origin at the button, translating up 14px on spatial-default, while the nine cells stagger in at 18ms intervals from the bottom-left cell (nearest the thumb) with a 6px rise. Closing reverses without the stagger, on exit.
  • Format apply. The tapped cell fills ember container in 150ms and pulses its corner radius once (26→30→26px). In the body, the affected text animates its own change — weight, slant or colour on the effects curve — so the eye is drawn to the text, not the button.
  • Undo / redo. The pressed arrow rotates 12° and springs back; the changed passage flashes an ink-container highlight that fades over 400ms and scrolls into view if off-screen. Holding either button repeats at 5 steps/second with one shared highlight, never one flash per step.
  • Snapshot. The ⏱ pill compresses, then a small chip lifts out of it carrying the new version's time and settles into the top-right of the screen before fading — the snapshot visibly leaves the button and goes somewhere. If history is open behind, the new dot springs into the timeline instead. Nothing blocks the editor; the pill returns to rest in 500ms.
  • Wikilink autocomplete. Opens by height only — 0 to auto on spatial-fast with no fade — because it must feel attached to the caret line. Rows re-rank in place as the user types, using a shared-element position spring so a row that stays in the list slides rather than reappearing. Accepting a suggestion collapses the list in 120ms while the raw [[…]] tokens cross-fade to the styled link.
  • Sort sheet. Rises 24px with a scrim at 40% over 200ms. Choosing a key dismisses the sheet immediately, and the list reorders after the sheet is gone: rows animate to new positions on spatial-default with a 12ms per-row stagger, and rows leaving the set fade at 0.9 scale. The sort button's mono label cross-fades to the new key.
  • View-mode change. The switcher morphs into the new rail label, then rows perform a grouped reflow: outgoing rows drop 8px and fade over 160ms, the new rails draw their hairline left-to-right in 220ms, incoming rows rise 10px with a 15ms stagger. Notes present in both modes keep identity and slide to their new position — going from list to folders should feel like the same notes rearranging, not a new screen.
  • Tag expander. The caret rotates 180°, the row's surface and mark colour shift on effects, and child rows expand by height with a 20ms stagger, each rising 6px. Expanding one tag collapses any other open tag in the same gesture, its rows leaving upward — a single continuous motion, so the list never appears to jump twice.
  • Folder drill-in. The tapped folder's mark and name are shared elements: the mark scales up into the breadcrumb while the file rows of the previous level clear downward and the new level rises. Back reverses exactly, restoring scroll position.
  • AI panel open. The ✦ button morphs into the cookie avatar in the sheet header while the sheet rises from the bottom edge on spatial-default with a 36px corner that eases from 48px, and the content behind dims to 45% and scales to 0.99 — receding, not disappearing. Quick-action chips stagger in at 20ms.
  • AI thinking and streaming. While waiting, the cookie avatar rotates slowly (8s per turn) with a 2px ink halo breathing at 1.4s — patient, not urgent. The response types in line by line; the diff block reveals row by row at 60ms intervals, additions wiping in from the left in moss, removals in red, and its +n −n count counts up as rows land. Action buttons animate in only when the proposal is complete, so nothing can be accepted mid-stream.
  • AI apply (single note). The sheet drops away first, then the edits land in the body one at a time, 90ms apart: each changed passage flashes moss and settles. Simultaneously the snapshot chip lifts from the ember pill, tying the change to the version that now protects it. A toast with "Undo" holds for 6 seconds.
  • AI apply (bulk). The plan list stays visible and each row completes in sequence: checkbox to a moss tick, count to "done", row dimming as it finishes, with a progress rule filling under the header. The sheet stays until every row has resolved, then collapses to a summary line "11 notes updated · Undo all". Failures stay in place, red, and are never dismissed automatically.
  • Version select and restore. Tapping a timeline dot expands the dot to 12px, springs the selected-version card to the new diff (old diff rows leaving upward, new ones entering from below), and moves the ember halo. Restore asks for confirmation in place — the pill widens into "Restore · takes a snapshot first" and requires a second tap — then transitions to the editor with the restored text arriving as a moss highlight sweep.
  • Search. Results replace on a 120ms crossfade with no reflow of the meta line; highlight spans grow their background from the centre out in 180ms. Scope chip changes re-filter without re-querying, so the change is instant by design.
  • Sync and state. Ember dots pulse once (scale 1→1.3→1) when a note enters the queue, and cross-fade to moss when it drains. Nothing spins persistently: an active sync shows a 2px moss progress rule under the docked bar's top edge.
  • Keyboard. The docked bar and any open menu ride the IME's own curve, tracking its height frame by frame rather than animating separately; the caret line is kept at least 96px above the keyboard, and the autocomplete list is clamped to the space between them.
  • Reduced motion. With the OS setting on, all springs become 120ms opacity fades, shape morphs land instantly at their end state, staggers collapse to zero, the AI avatar stops rotating, and highlights still appear but do not sweep. Every state must be reachable and legible with all motion removed.

7 · States still to design

The nine screens cover the resting and success paths. The following states should be drawn before build, in the same grammar: an empty vault and an empty tag; index-rebuilding (rail count replaced by a stale marker); server unreachable (the docked bar keeps working, the search rail says "offline cache"); a sync conflict banner offering "keep mine / keep theirs / open both"; the keyboard-up editor at its smallest usable height; the sort sheet and the long-press note menu in their open states; and a name-this-snapshot sheet for versions the user wants to find later by name rather than by time.
